Статус: черновик для владельца (2026-11-28), ревизия 4. Рабочее дерево `/projects/readfine/ui-redesign`, ветка `feat/animations`, основа `8281192`.
Связанные документы: [дизайн редизайна UI](2026-11-19-ui-redesign-design.md) (§5.3 «Foundation», §5.5 «DOM contract and offline», §6 «Invariants»), `/projects/readfine/specs/log-decisions.md`, `/projects/readfine/specs/backlog.md`.

Пометка «**решение планировщика**» стоит у каждого выбора, который сделал я, а не владелец. Владелец может отменить любой из них. Вопросы, которые может решить только владелец, собраны в §15.

## Коротко для владельца (ревизия 4)

1. **Что значит «через anime.js».** Я читаю это так: каждую анимацию в приложении запускает публичный API anime.js 4.5.0, и только из `motion.js`. Это модуль WAAPI из anime (`anime.waapi.animate`). Пружины строит `anime.spring` и переводит в кривую `anime.waapi.convertEase`. Прямых вызовов браузерного `Element.animate` в обход anime нет. Если anime.js не загрузился, анимации нет вовсе: состояние уже нарисовано правильно, и слой ничего не дописывает. JS-движок anime (`anime.animate`) пресеты не используют. Он пишет inline-стиль каждый кадр, запускает CSS-переходы кнопок (двойная анимация), не виден в `document.getAnimations()` и не останавливается в визуальных тестах. Модуль WAAPI из anime лишён этих недостатков. Его единственная ловушка в том, что после конца он оставляет inline-стили. Её закрывает одно правило очистки, проверенное в Chrome (§3, §6.1). В ревизии 2 разрешался и прямой `Element.animate`, теперь он убран. В распоряжении упомянут `createSpring`, но в этой версии anime он устарел и пишет предупреждение в консоль, поэтому используется `anime.spring`. Это та же функция под новым именем.
2. **Счётчики.** Цель 4 говорит про «анимированные счётчики». Теперь это значит: бейдж делает короткий пружинный «поп» в момент смены числа. Бегущие цифры поверх бейджа убраны. Для них нужен был отдельный слой копий над бейджем, это самая хрупкая часть ревизии 2 (наложение на полноэкранную статью, очистка), а отклик и так виден.
3. **Удаление строки.** Удалённая строка исчезает сразу, соседи плавно подъезжают на её место. Это техника FLIP: элемент мгновенно встаёт на новое место, затем визуально «доезжает» от старого. Гаснущих копий удалённой строки больше нет.
4. **Переход при открытии статьи.** Сама анимация длится не дольше 165 мс. Пауза ввода чуть дольше: к анимации добавляются снимок старого и нового состояния и свап, это несколько кадров (§6.6.2, инвариант 3).
5. **Нажатие.** Кнопка не «держится» вдавленной под пальцем. В момент касания она коротко ныряет примерно до 0,94 и пружиной возвращается назад с лёгким перелётом. Всё это одна анимация не дольше 165 мс, а отпускание пальца ничего не запускает. Отклик остаётся живым и пружинным, но длится одинаково при коротком тапе и при долгом удержании. Так нажатие подчиняется тем же правилам очистки, что и все остальные анимации (§6.4.3).

**Что изменилось в ревизии 4** (по второй проверке дизайна):

1. Нажатие: один вызов на `pointerdown`, кадры `[1, ~0,94, покой]`, пружина `press`, всего ≤ `--t-fast-max`, без удержания; на `pointerup` ничего. Токен `--t-press` убран (§6.3, §6.4.3, §7, инвариант 5).
2. Правило 3 обёртки: перед чтением покоящегося значения `run()` останавливает свои живые анимации того же элемента и свойства. Для `scale` и `translate` покой — объявленный `none`. Пресет `opacity` пропускается, если по `opacity` идёт CSS-переход. Лист сайдбара при закрытии — явное исключение по `visibility` (§6.1, §6.5).
3. FLIP: снимок на `beforeSwap`/`oobBeforeSwap` только у запросов, которые не помечены как опрос; снимок у клика покрывает только синхронные удаления. Случай «архив убирает строку» удалён: такого пути в коде нет (§6.4.2, §6.4.4, §7).
4. Мелочи: остаточный тождественный переход учитывается и для `translate`; исключения и область `check-motion-calls.mjs`, галерея в разрешённом списке; метка времени для вето 300 мс ставится в обёртке; снятие `html[data-rf-vt]` для каждого перехода (§6.4.3, §6.6.2, §9).

**Что изменилось в ревизии 3** (по проверке дизайна; каждое утверждение перепроверено по `vendor/anime/anime.umd.min.js` 4.5.0, `htmx.min.js` 2.0.4 и пробой в Google Chrome 158, см. §3):

1. Один движок: `anime.waapi.animate`. Очистка идёт через `revert()` в `onComplete`, ключевые кадры задаются только массивами, последний кадр равен покоящемуся значению, `persist` не используется, останов идёт через нативный `cancel()`. Прямой `Element.animate` убран (§6.1, §6.12, инвариант 4).
2. Пружины: в 4.5.0 их `settlingDuration` равен 440–740 мс даже при `bounce = 0`. Цикл «понижать bounce» бюджет 165 мс не выполнит никогда. Он заменён обрезкой кривой на бюджете (§6.3).
3. View Transition, который запускает htmx: `motion.js` один раз оборачивает `document.startViewTransition`. Атрибут `html[data-rf-vt]` ставит обёртка и снимает по `finished`. Опрос `getAnimations()` и таймер-страховка убраны (§6.6.2).
4. Призраки удалены. Выход строк — FLIP соседей. Счётчики — поп бейджа. `#rf-motion-layer` остаётся только для частиц звезды, и они не рисуются, если звезда закрыта другим слоем (§6.4.2, §6.4.6).
5. Мелкие правки: `settle:0ms` в override перехода, честная формулировка паузы ввода, точный признак «стал видимым», один владелец анимации на каждую пару «статья и состояние», строки инвентаря для `<details>`, вкладок, приветствия, share target и подсказок релевантности, защита override, цель `fade-up-short` в статье (§6.4, §6.6.2, §7).

Ревизия 2 (кратко, всё в силе): переход открытия статьи включается через `detail.swapOverride`, снимок офлайн не меняется; правило «тот же id — это обновление» общее для всех путей; шесть мест смены полноэкранных классов обёрнуты одним помощником; CSS перехода внутри читалки ограничен `html[data-rf-vt]`; правило `[data-motion]` под reduced motion переписано на 0,01 мс.

## 1. Замысел

Сейчас интерфейс почти неподвижен. Слой анимации есть (`static/js/ui/motion.js`, anime.js 4.5.0 подключён), но им почти никто не пользуется. Владелец хочет, чтобы каждое нажатие, переход, смена состояния и действие получали заметный отклик: человек нажал, и видно, что приложение отозвалось.

Зачем это нужно:

- **Обратная связь.** Звезда, «прочитано», удаление, Undo, сохранение настройки сейчас меняют состояние без перехода. Глаз пропускает такую перемену, и человек не уверен, что действие сработало.
- **Где я и откуда это пришло.** Список меняется целиком, статья появляется, лист открывается, и всё это без перехода. Короткое движение показывает, что именно сменилось.
- **Характер.** Владелец выбрал «живой» характер: пружины, каскады, счётчики. При этом частые действия (j/k, прокрутка, отметка прочитанного) остаются короткими.

## 2. Цели, не-цели, анти-цели

**Цели**

1. Каждое действие и каждая смена состояния во всём веб-приложении (читалка, настройки, источники, ассистент, вход, админка) получают видимый отклик. Полный перечень в инвентаре §7.
2. Один центральный слой поверх `motion.js`. Общие события подключены один раз: нажатие на любую кнопку или ссылку, появление контента после htmx-свапа, открытие и закрытие диалогов, меню, панелей, тосты. Шаблоны и UI-макросы только объявляют намерение через `data-motion…`. Особые эффекты (звезда, счётчики, волна «прочитать всё», свайпы) живут в том же слое как именованные пресеты.
3. Навигация между экранами и открытие статьи идут через View Transitions, анимация которых длится не больше 165 мс.
4. Характер «живой»: пружины на нажатиях, звезде и панелях, каскад при появлении списков, отклик счётчиков (поп бейджа, см. «Коротко для владельца», п. 2), короткие частые действия.
5. Все действующие правила сохраняются: reduced motion убирает движение, анимация никогда не блокирует ввод, офлайн работает, CSP не меняется.

**Не-цели**

- Новые элементы интерфейса или новое поведение: полоса обратного отсчёта Undo, жест «смахнуть, чтобы закрыть» статью на телефоне, звук, вибрация. Это возможные продолжения, см. §15.
- Анимация самостоятельных страниц, которые строит service worker: офлайн-страница `offlinePage` в `static/js/offline/templates.js` и страница запуска `static/js/offline/launch.js`. Наши скрипты там не грузятся, и у них своя, уже утверждённая анимация (`launch.js:21`, вариант C).
- Публичные страницы (`templates/public/base.html:6,28`: только `init.js`, без htmx и motion.js) получают только кросс-документный переход между страницами из CSS (§6.6). JS-анимации там нет.
- Письма (шаблоны email).
- Перенос анимаций Basecoat в JS там, где CSS Basecoat уже даёт нужный выход и не мешает вводу (§6.5).

**Анти-цели (чего делать нельзя)**

- Вызывать anime.js вне `motion.js`, разносить вызовы анимации по модулям или писать inline-скрипт в шаблонах (кроме галереи разработчика `/dev/ui`, инвариант 9). Владелец этот путь отверг. Анимировать в обход anime.js (прямой `Element.animate`) тоже нельзя (§6.1).
- Задерживать изменение состояния ради анимации: свап, удаление строки, закрытие диалога выполняются сразу, анимация только догоняет.
- Писать текст или менять структуру в элементах, которыми владеет другой код: `app.js` читает `textContent` бейджей (`app.js:1101, 2666`), поэтому анимация счётчика не трогает их текст (§6.4.6).
- Оставлять после анимации inline-стили. Строки «прочитано» держатся на классе `opacity-75` (`article_row.html:293`), и inline `opacity: 1` его перебьёт. Как это обеспечено при движке anime WAAPI, см. §6.1.
- Анимировать `width`, `height`, `top`, `left` и другие свойства, которые запускают раскладку. Разрешены только `transform` (и отдельные свойства `scale`, `translate`), `opacity`, а для вспышки цвет фона через CSS.
- Добавлять в шаблоны из замыкания офлайн-снимка атрибуты, без которых можно обойтись (§6.7).

## 3. Ограничения (из кода и прошлых решений)

- **Один модуль анимации, без inline anime.js.** Дизайн редизайна, §4 и §5.3: `motion.js` держит токены, проверку reduced motion и htmx-хуки, шаблоны объявляют намерение через `data-motion`.
- **Только статические `<script src>`.** Offline shell cache находит скрипты по тегам в `base.html` (дизайн, §5.5; `base.html:557-562`). Динамический `import()` запрещён. Новый файл добавляется отдельным статическим тегом.
- **Порядок загрузки.** `anime.umd.min.js` (`base.html:563`), Basecoat (`:564-572`), `ui/toast.js`, `ui/settings.js`, `ui/pending.js`, затем `ui/motion.js` (`:576`), `ui/dialog.js` (`:577`), `ui/sources.js` (`:578`), `app.js` (`:579`). Все с `defer`. `ui/toast.js`, `ui/settings.js` и `ui/pending.js` загружаются **раньше** `motion.js`, поэтому на порядок загрузки опираться нельзя. Правило такое: слушатели, которым нужно сработать раньше модулей (снимок перед удалением, §6.4.2; старое значение звезды, §6.4.4), слой ставит **в фазе capture** на `document`. Модули слушают в фазе всплытия на `document` или `body` (например, `pending.js:351` — клик по `[data-rf-delete]`; `app.js:2631` — `articleStarChanged`; `app.js:700` — `savedArticleRemoved` на `body`). Capture-слушатель на `document` срабатывает раньше любого всплывающего слушателя, в каком бы порядке их ни поставили. Если событие отправлено на сам `document` (оптимистичная звезда, `app.js:2732`), по текущей спецификации DOM capture-слушатели на цели тоже идут первыми (Chrome 89+, Safari 15+).
- **`prefers-reduced-motion: reduce` убирает любое движение**, View Transitions тоже (дизайн, §6, строка 261). Анимации anime.js никогда не блокируют ввод. Единственная допустимая пауза ввода — View Transition (анимация не длиннее 165 мс, §6.6.2), и запущенный переход пропускается, если начинается новый.
- **Отказ JS** (холодный офлайн-старт, блок CSP): приложение работает без анимации, состояние уже правильно отрисовано сервером (дизайн, §5.6).
- **CSP:** `script-src 'self' 'nonce-…'`, без `unsafe-eval`, `htmx.config.allowEval = false` (`base.html:534`). `style-src` разрешает inline-стили (`main.py`), поэтому inline-стиль во время анимации допустим.
- **Цвета только из токенов** (`scripts/check-colours.mjs`). Цвет частиц звезды и вспышек берётся из `--rf-star`, `--rf-flash` и других токенов.
- **Офлайн-снимки.** Шаблоны снимка (`article_row.html`, `article_detail.html` и их include) закреплены хешем `OFFLINE_TEMPLATE_HASH` рядом с `OFFLINE_TEMPLATE_VERSION = "7"` (`backend/app/services/sync/__init__.py:5-9`). Любая правка там требует зеркала в `templates.js`, перегенерации golden-файлов drift-теста и повышения версии.
- **DOM-контракт.** `docs/ui-dom-contract.md` и `npm run check:sources` → `check-dom-contract.mjs`: каждый id, `data-*` и класс, на который опирается JS, должен быть записан в контракте.
- **anime.js 4.5.0, модуль WAAPI** (прочитано в `vendor/anime/anime.umd.min.js`, класс `WAAPIAnimation`, помощники фиксации и `Ke`; поведение подтверждено пробой в Chrome 158 через Playwright, ревизия 3):
  - `anime.waapi = {animate, convertEase}`. `animate` создаёт **по одной нативной анимации на каждый ключ** с `fill: "both"`;
  - без `persist: true` по окончании каждой анимации (а также по `cancel` и `remove`) срабатывает внутренний помощник: `commitStyles()`, затем `cancel()`. Конечное значение **записывается в inline-стиль**. Проба: `opacity: [0, 1]` без очистки оставляет `style="opacity: 1;"`. Новая анимация того же элемента и того же свойства тем же путём фиксирует и отменяет прежнюю;
  - объектная форма ключа `{from, to}` пишет `from` в inline-стиль сразу при создании (проба: `style="opacity: 0;"`). Форма массивом ничего не пишет;
  - при создании экземпляр запоминает исходные inline-значения каждого ключа (`_inlineStyles`). `revert()` вызывает `cancel()` и восстанавливает их, пустое значение удаляется, пустой атрибут `style` снимается. Проба: если `revert()` вызвать внутри `onComplete`, `style` остаётся пустым после конца, после нативного `cancel()` из визуального харнесса (`key-screens.spec.mjs:339-343`), после нативного `finish()` (так `animations: 'disabled'` у Playwright доводит анимацию до конца), при перебивании новой анимацией того же свойства и после `complete()`. Заранее стоявший inline-стиль (`opacity: 0.3`) восстанавливается, а не стирается. Inline `transform`, который записал чужой код во время анимации `translate`, `revert()` не трогает;
  - **ловушка:** если вызвать `revert()` или `cancel()` экземпляра посреди полёта, нативное событие `cancel` придёт позже и снова зафиксирует значение. Проба: сразу после `revert()` стиль пуст, а через кадр в нём `opacity: 1`. Чистый останов посреди полёта — нативный `cancel()` у анимаций экземпляра или `complete()`: тогда фиксация и `onComplete → revert()` идут в одном обработчике (проба: стиль пуст);
  - ключи: голые `opacity`, `scale`, `translate`, `transform` анимируют одноимённые CSS-свойства (проба: в ключевых кадрах `scale`, inline `transform` не тронут). Если в том же вызове есть любой из ключей `x`, `y`, `z`, `translateX`, `scaleX` и подобных, anime пишет inline `transform: scale(var(--scale)) translateX(var(--translateX))`, а после `revert()` остаются inline `--scale` и `--translateX`;
  - пружина в `ease` переводится в `linear()` из 101 точки, длительностью WAAPI становится её `settlingDuration` (проба: `bounce 0,35, duration 140` → 440 мс);
  - `anime.createSpring` устарел и пишет `console.warn`, правильное имя — `anime.spring`.
- **htmx 2.0.4** (проверено в `static/js/htmx.min.js`, ревизии 2 и 3):
  - сам вызывает `document.startViewTransition(cb)`, если в разобранной спецификации свапа есть `transition:true` (или включён `htmx.config.globalViewTransitions`; у нас он выключен). Перед этим htmx шлёт отменяемое событие `htmx:beforeTransition` на элементе запроса, `detail` — это `responseInfo` с `target`. Событие идёт **до** проверки наличия API. Объект `ViewTransition` htmx никому не отдаёт, но берёт `document.startViewTransition` в момент вызова, поэтому обёртка, которую поставил `motion.js`, видит и htmx-переходы (§6.6.2). Колбэк обновления выполняет свап и возвращает промис, который разрешается в конце settle (`afterSettleCallback`) и отклоняется при ошибке свапа;
  - **settle.** Задержка settle по умолчанию 20 мс (`htmx.config.defaultSettleDelay`, `base.html:534-537` её не меняет). Модификатор `settle:0ms` выполняет settle синхронно сразу после свапа (`if (settleDelay > 0) setTimeout(…) else doSettle()`);
  - **`detail` события `htmx:beforeSwap` содержит `swapOverride`.** htmx собирает его из `htmx.ajax(…, {swap})` и заголовка `HX-Reswap`, отправляет событие, затем читает поле обратно (`g=m.swapOverride`) и разбирает спецификацию через `gn(elt, g)`. `gn` берёт **либо** override, **либо** `hx-swap` элемента, не сливая их. Значит, override должен нести полную спецификацию: стиль свапа плюс все модификаторы. Это публичное поле `detail` в htmx 2, а не обход через `detail.etc`;
  - `triggeringEvent` есть в `detail` событий `htmx:confirm` и `htmx:configRequest`;
  - **OOB-свапы.** `hx-swap-oob` обрабатывается раньше основного свапа, с тем же `settleInfo`. В стиле `outerHTML` новые элементы попадают в `settleInfo.elts`, и в конце htmx шлёт `htmx:afterSwap` **на каждый** из них. При этом `detail` — это `eventInfo` основного запроса, то есть `detail.target` указывает на основную цель, а не на OOB-цель. OOB в стиле `innerHTML` (например, `label-badge-*` из `routers/web/app/articles.py`) в `elts` ничего не добавляет и своего `afterSwap` не получает. Кроме того, htmx шлёт `htmx:oobBeforeSwap` на OOB-цель (`detail.target`, `detail.fragment`, отменяемое) и `htmx:oobAfterSwap` на **все** элементы, накопленные в `settleInfo.elts` к этому моменту, включая основную цель. Поэтому событие `oobAfterSwap` шумное, и слой на него не опирается (§6.4.1). Все OOB-фрагменты в шаблонах, роутерах и офлайн-воркере (`static/js/offline/router.js:126-127, 495`, `templates.js:208-211`) сегодня — обновления на месте (строки, бейджи, метки, ИИ-блоки, счётчики) или `delete`.
  - **Перенос атрибутов при замене (settle).** Перед вставкой htmx ищет в документе элемент с тем же id, что у нового (`Le` в `a()`). Если находит, копирует на новый элемент **старые** значения `class`, `style`, `width`, `height` (`htmx.config.attributesToSettle`) и возвращает новые значения только в задаче settle, перед `htmx:afterSettle`. Значит, на `afterSwap` заменённая строка ещё несёт старые классы. Атрибуты `data-*` и `hx-*` не переносятся;
  - спецификация свапа берётся через `re(elt, "hx-swap")`, а это **наследуемый** поиск: ближайший `hx-swap` у элемента или предков, иначе `htmx.config.defaultSwapStyle`.
- **История.** `historyCacheSize = 0`, `refreshOnHistoryMiss = true` (`base.html:535-536`): «назад» перезагружает страницу.

## 5. Варианты подхода

**A. Центральный слой поверх `motion.js` (выбран владельцем).** Все анимации и все подписки на события живут в `motion.js`. Шаблоны объявляют намерение атрибутами. Особые эффекты — именованные пресеты, привязанные к уже существующим событиям и хукам DOM-контракта.
- Плюсы: одно место для reduced motion, пределов длительности, правил ввода и тестов. Модули не меняются или меняются точечно. Отклик единообразный.
- Минусы: слою нужно знать моменты «до» и «после» чужих изменений. Для FLIP при удалении нужны прямоугольники соседей до удаления. Это делается перехватом событий в фазе capture и MutationObserver (§6.4.2). Слой растёт.

**B. Вызовы `RFMotion` в каждом модуле (отвергнут владельцем).** `app.js`, `pending.js`, `shell.js` и другие сами вызывают анимацию там, где меняют DOM.
- Плюсы: момент «до» всегда известен, выход строится просто.
- Минусы: десятки вызовов в больших файлах (`app.js` — 3951 строка), легко забыть reduced motion или очистку, двойные анимации, нет единого теста «у каждого действия есть отклик».

**C. Только CSS плюс View Transitions (отвергнут владельцем).** Переходы в `input.css`, `@starting-style`, `transition-behavior: allow-discrete`, View Transitions на навигации.
- Плюсы: ноль JS, работает даже без скриптов, браузер сам ведёт анимацию на композиторе.
- Минусы: нет пружин, каскада с пределом, частиц звезды. Смену состояния (звезда, прочитано, счётчик) CSS видит только как смену класса. Оптимистичная звезда, которая придёт ещё дважды, даст три анимации. FLIP соседей после удаления CSS не умеет.

Выбран вариант A. Из C взято то, где CSS лучше: выход диалогов и меню через `allow-discrete`, кросс-документный View Transition, цветовые вспышки.

## 6. Дизайн

### 6.1 Строение слоя

- **Файл.** Остаётся один `static/js/ui/motion.js` с разделами: ядро (токены, reduced, пределы, обёртка движка), регистр пресетов, проводка событий, FLIP и частицы, View Transitions, трассировка для тестов. **Решение планировщика:** если файл перерастёт примерно 800 строк, строитель может вынести пресеты в `static/js/ui/motion-presets.js`. Это отдельный статический тег сразу после `motion.js` в `base.html`, тот же слой и тот же владелец. Появление второго файла фиксируется в DOM-контракте и в `CLAUDE.md`.
- **Защита от двойной загрузки:** `if (window.RFMotion) return;` в начале. Подписки и обёртка `startViewTransition` ставятся один раз.
- **Один движок: `anime.waapi.animate`.** **Решение планировщика.** Все пресеты идут через модуль WAAPI из anime. Прямого `Element.animate` нет. JS-движок `anime.animate` пресеты не используют. Если `window.anime` или `anime.waapi` нет, пресет не играется: конечное состояние уже в DOM, слой ничего не пишет. Почему WAAPI-модуль, а не JS-движок anime с очисткой:
  1. WAAPI работает на композиторе и не дёргает главный поток каждый кадр.
  2. Начальный кадр применяется в том же задании, где анимацию создали (`fill: "both"`), поэтому в первом кадре после свапа не мелькает конечное состояние (это T17-R3 из `backlog-resolved.md:43`).
  3. WAAPI-анимации видны в `document.getAnimations()`. Существующие e2e-проверки и `animations: 'disabled'` в визуальных тестах начинают их видеть.
  4. Пока анимация идёт, WAAPI не трогает inline-стиль и не запускает CSS-переходы элемента. JS-движок пишет inline-стиль каждый кадр, и `transition-all` на `.btn` каждый раз запускал бы переход: двойная анимация.
  5. Цена — inline-фиксация в конце (§3). Её закрывают пять правил ниже, а проверены они пробой в Chrome. Бороться с фиксацией дешевле, чем со всеми недостатками JS-движка из п. 1–4.
- **Пять правил обёртки движка** (одна внутренняя функция `run(target, keyframes, opts)` в ядре, через неё идут все пресеты):
  1. **Очистка в `onComplete`.** Каждый вызов `anime.waapi.animate` получает `onComplete: a => a.revert()`. Внешний `onComplete` пресета вызывается после очистки. Нативные `finish`, `cancel` и перебивание новой анимацией того же свойства тоже приходят в `onComplete`, поэтому очистка срабатывает на всех путях (проба, §3).
  2. **Ключевые кадры только массивами.** Объектная форма `{from, to}` запрещена: она пишет `from` inline при создании.
  3. **Последний кадр равен покоящемуся значению.** Тогда фиксация в конце пишет то же значение, что даёт CSS, и после `revert()` вычисленный стиль не меняется. Для прочитанной строки это `0.75`, а не `1`, и CSS-переход строки (`base.html:140`) не срабатывает. Проба: при конце на `1` после `revert()` запускается переход `opacity` строки, при конце на покоящемся `0.75` переходов ноль. Все ключи одного вызова имеют одну длительность, поэтому заканчиваются в одном кадре. Откуда берётся покой (**решение планировщика**):
     - **Сначала останов своих.** Перед чтением `run()` вызывает `handle.stop()` у своих живых анимаций **того же элемента и того же свойства**, какой бы пресет их ни запустил (нажатие и `star-on` на одной кнопке звезды, нажатие и `count-pop` на бейдже, два быстрых нажатия). Нативный `cancel()` снимает эффект синхронно, а поздняя очистка в anime остаётся чистой (правило 5). Иначе `getComputedStyle` вернул бы значение посреди чужого полёта, и новая анимация закончилась бы на устаревшем значении.
     - **`scale` и `translate`:** покой — объявленный `none`, без чтения. Вычисленный стиль читается, только если у элемента это свойство задано (вычисленное значение не `none`).
     - **`opacity`:** покой читается из `getComputedStyle` цели после того, как конечное состояние уже применено. Если по `opacity` у цели идёт `CSSTransition` (`el.getAnimations()`; например, строка только что стала прочитанной, `base.html:140`, или переход `htmx-indicator` под `busy-in`), пресет на этой цели не запускается: состояние и так правильное, а вычисленное значение посреди перехода устарело бы. Этот пропуск касается только `opacity`. Тождественный переход `scale` или `translate` после `revert()` (§6.4.3) нажатие не глушит.
     - **Исключение: закрытие телефонного листа сайдбара** (§6.5). Ключ `visibility: [visible, visible]` заканчивается не на покое (CSS стоит на `hidden`). Это единственное исключение из правила 3, оно записано в регистре пресетов и проверено юнит-тестом (§9, п. 10). Фиксация и `revert()` идут в одном обработчике, поэтому inline `visibility` не остаётся.
     - Если за время полёта CSS-значение того же свойства сменилось (`fill: "both"` на это время его перекрывает), новое значение становится видно в конце полёта, после `revert()`, через CSS-переход элемента, если он есть. Полёты короткие (≤ `--t-med-max`), это принято.
  4. **`persist` не задаётся никогда.** При `persist: true` с `fill: "both"` анимация держит значение вечно (проба: анимация жива после конца).
  5. **Останов посреди полёта** — только `handle.stop()` (снаружи, а также внутри `run()` по правилу 3). Он вызывает нативный `cancel()` у анимаций экземпляра (или `complete()`), а очистку делает правило 1. `revert()` и `cancel()` экземпляра anime напрямую не вызываются: нативное событие `cancel` придёт позже и снова зафиксирует значение (проба, §3). Наружу `play` отдаёт только `{stop, finished}`.
- **Ключи — только родные имена CSS-свойств.** Разрешены `opacity`, `scale`, `translate`, а для листа сайдбара `transform` и `visibility` (§6.5). Ключи `x`, `y`, `z`, `translateX`, `scaleX` и подобные запрещены: они пишут inline `transform` с `var(--…)`, затирают `transform` свайпа из `read.js` и оставляют `--scale` и `--translateX` после `revert()` (проба, §3). Нажатие и «поп» анимируют `scale`, сдвиги — `translate`. Так они не спорят с inline `transform` свайпа и с Basecoat: Tailwind 4 задаёт панели диалога и листа через `translate` и `scale`, а не через `transform` (проверено в собранном `static/css/tailwind.css`: `.drawer[data-side=bottom]>*{… translate:var(--tw-translate-x) var(--tw-translate-y) …}`). Во время WAAPI-анимации того же свойства анимация перекрывает CSS-переход, а это и нужно (§6.5). Белый список ключей проверяет юнит-тест по регистру пресетов (§9, п. 10).
- **Пружины** — через `springEase(name)` (§6.3): `anime.spring` плюс `anime.waapi.convertEase`, обрезка на бюджете.
- **API `RFMotion` (дополнения).** Существующие поля остаются с прежним контрактом, кроме `animate` и `stagger` (см. ниже):
  - `RFMotion.play(name, target, opts) → {stop, finished} | null`: запустить пресет по имени. Это единственный вход для кода вне слоя. В этой работе его вызывают только два модуля: `read.js` (§6.4.5) и `feeds-settings.js` (§6.8).
  - `RFMotion.presets`: регистр (только чтение снаружи).
  - `RFMotion.activeCount()` и `RFMotion.idle() → Promise`: сколько анимаций и частиц живо сейчас, и обещание, что закончатся они и текущий View Transition. Нужны тестам и визуальному харнессу.
  - `RFMotion.trace`: журнал запусков пресетов `{name, target, t}`. Он включается, только если на `<html>` стоит `data-rf-motion-trace`, а этот атрибут тесты ставят через `addInitScript`. В продакшене журнал пустой.
  - `RFMotion.transition(update, opts)` остаётся. Старый вызов `transition(update)` работает как раньше. Новые необязательные `opts = {key, scope}`: `key` склеивает повторы (§6.6.1), `scope` — значение `html[data-rf-vt]` на время перехода (§6.6.2). Ещё добавляется внутренний сброс отложенного обновления (§6.6.1). Из модулей `transition` вызывается только через помощник `_shellTransition` в `app.js` (§6.6.1).
  - `RFMotion.animate` (единственный путь через JS-движок anime) и `RFMotion.stagger` после этапа 4 не имеют вызывающих: `read.js` переходит на `play` в этапе 2, `feeds-settings.js` — в этапе 4. **Решение планировщика:** в этапе 4 оба поля удаляются вместе с их юнит-тестами в `motion.test.mjs`, и в слое остаётся один движок. До этапа 4 `animate` сохраняет нынешний контракт.

### 6.2 Словарь объявлений в шаблонах

Атрибутов мало, у каждого одно значение.

| Атрибут | Где | Что значит |
|---|---|---|
| `data-motion="<пресет появления>"` | элемент или контейнер | Проиграть пресет появления, когда элемент приходит в DOM свапом или становится видимым (§6.4.1). На контейнере-цели свапа `innerHTML` пресет играется **при каждом** свапе в этот контейнер, для нового содержимого. Это исправляет T17-R2. |
| `data-motion-flip` | контейнер, из которого уходят элементы | Когда ребёнок удалён или скрыт, оставшиеся видимые дети подъезжают на новое место (FLIP, §6.4.2). |
| `data-motion-press="off"` или `="soft"` | кнопка, ссылка, строка | Отключить нажатие или включить мягкое нажатие для крупных целей. По умолчанию нажатие есть у всех интерактивных элементов (§6.4.3). |
| `data-motion-count` | число на экране, если на него нет готового хука | Поп при смене числа (§6.4.6). |
| `data-motion-skip` | контейнер | Внутри не проигрывать появление: опрос, фоновые обновления. |
| `data-motion-transition="<scope>"` | цель свапа | Открытие в эту цель по доверенному клику идёт через View Transition. Полную спецификацию свапа слой ставит в `htmx:beforeSwap` через `detail.swapOverride` (§6.6.2). Сейчас атрибут один: `data-motion-transition="detail"` на `<main id="article-detail">` (`main.html:321`, вне замыкания снимка). Значение `data-motion` здесь не подходит: у цели свапа оно значит «проиграть появление». **Решение планировщика.** |

Особые эффекты (звезда, прочитано, волна, свайп, счётчики сайдбара, FLIP списка статей) привязываются **к уже существующим хукам DOM-контракта** в регистре пресетов внутри `motion.js`: `[data-star-btn]`, `[data-bottom-star]`, `[data-header-star]`, `#article-row-*`, `#article-list` (как FLIP-контейнер), `[data-saved-count]`, `#label-badge-*`, `#mobile-title-count` и другие. Так шаблоны из замыкания офлайн-снимка не меняются (§6.7). **Решение планировщика.**

UI-макросы объявляют намерение сами, чтобы страницы не повторяли его: `ui/overlay.html` для `dialog`, `sheet`, `menu`, `popover`, `toast`, `ui/display.html` для `alert`, `empty_state`, `card`, `skeleton`, `ui/forms.html` для `field` и ошибки поля. Параметр `motion=none` в макросе отключает объявление.

- **Пружины обрезаются на бюджете.** **Решение планировщика.** Заменяет цикл «понижать bounce» из ревизии 2: у anime 4.5.0 `settlingDuration` считается до полного покоя и равен 360–740 мс даже при `bounce = 0` (§4), так что бюджет 165 мс не достигается никогда. `springEase(name)` строит `s = anime.spring({bounce, duration})`, берёт `k = min(1, бюджет / s.settlingDuration)` и отдаёт `{ease: anime.waapi.convertEase(t => s.ease(t·k) / s.ease(k)), duration: min(s.settlingDuration, бюджет)}`. Это та же пружина, у которой отрезан невидимый хвост покоя. Проба на настоящем бандле: остаток хвоста после точки обрезки — 0,5 % у `press`, 1,1 % у `snap`, 0,08 % у `panel`, 0 у `pop`. Нормировка на `s.ease(k)` ставит последний кадр точно в 1, поэтому правило 3 из §6.1 выполняется. Юнит-тест на настоящем `anime.umd.min.js` (§9, п. 3) проверяет каждую именованную пружину: длительность ≤ бюджета и `|1 − s.ease(k)| ≤ 0,02`. Если строитель подберёт числа, при которых остаток больше 2 %, он понижает `bounce` у этой пружины.
- Новый мягкий предел: частое действие (нажатие, j/k, прочитано, свайп-возврат, поп счётчика) укладывается в `--t-fast-max`, считая пружину.

### 6.4 Проводка

#### 6.4.1 Появление (enter)

- **Когда.** Три источника:
  1. `htmx:afterSwap`, как сейчас. Событие приходит на основную цель и на каждый новый элемент `outerHTML`-свапа, основного или OOB (§3). Цель события и есть элемент, который нужно классифицировать (правило 4 ниже). `htmx:oobAfterSwap` для появления не используется: оно приходит на все элементы `settleInfo`, в том числе на основную цель.
  2. Новые дети, которые JS добавил в контейнер с `data-motion` без htmx: пузыри чата (`assistant.js:636-637`), ошибка чата (`assistant.js:247`), тосты в `#toaster`, баннер в офлайн-слоте, модалка выхода. Их видит тот же MutationObserver (`childList`). Правило одно для htmx и для JS: **контейнер с `data-motion` проигрывает свой пресет на каждом новом ребёнке**.
  3. Элементы с `data-motion` (и селекторы из регистра, например `[role=tabpanel]`, §6.5), которые **стали видимыми**. Наблюдатель: `attributeFilter: ['hidden', 'class', 'aria-hidden', 'open']` с `attributeOldValue: true`. «Стал видимым» значит одно из четырёх: атрибут `hidden` снят; `aria-hidden` было `true` и стало другим; `open` появился; в старом значении `class` был токен `hidden`, а в новом его нет. Любая другая смена `class` не считается: `htmx-request`, `htmx-swapping`, `htmx-settling`, `htmx-added`, `active` и прочие, которые htmx и модули ставят на контейнеры вроде `#article-list` при каждом запросе. После этого элемент ещё раз проверяется через `checkVisibility()`. Смены `class` у элементов из `replacing` в момент settle пропускаются (правило 4).

  Обработчик наблюдателя сначала проверяет `hasAttribute('data-motion')` или совпадение с регистром у узла или его родителя, поэтому стоит копейки.
- **Навигация против обновления.** Без этого правила появление проигрывалось бы каждые 300 с при обновлении сайдбара (`main.html:300-304`), на каждом OOB-обновлении строки (`article_row.html:292`), на опросах и подгрузке страницы. Правило такое:
  1. Пресет появления объявляют только на целях **навигации**: `#article-list`, тело листа `#rf-source-sheet-body`, результаты палитры, разделы страниц. На целях фонового обновления (`#sidebar`, опросы `row_poll`, `readable_progress`, опрос ИИ-сводки) его не объявляют, а там, где тело может прийти и так и так, ставят `data-motion-skip`.
  2. Свап, запрос которого начат опросом (`hx-trigger` с `every`, `load` внутри уже показанного контента, событие `sidebarRefresh`), появление не проигрывает. Слой помечает такие запросы на `htmx:configRequest` по `detail.triggeringEvent` (поле есть, §3) и по атрибуту `hx-trigger` элемента, а на `afterSwap` читает пометку по элементу запроса.
  3. Подгрузка страницы (`article_list_append.html`, сторож пагинации) играет `list-enter` только на новых строках, с тем же пределом в 10.
  4. **Замена на месте — это обновление, а не появление.** **Решение планировщика.** Единый признак для всех путей (`afterSwap`, наблюдатель, FLIP) — **тот же id до и после**. Слой держит множество `replacing` — id элементов, которые сейчас заменяются:
     - `htmx:oobBeforeSwap` (capture на `document`): `detail.target.id` попадает в `replacing`, если в `detail.fragment` есть элемент с тем же id. Это самый ранний и **главный** сигнал OOB-обновления: он приходит до изменения DOM;
     - `htmx:beforeSwap`: если разобранный стиль основного свапа — `outerHTML` (`detail.swapOverride`, иначе наследуемый `hx-swap`, иначе `htmx.config.defaultSwapStyle`, §3), id `detail.target` попадает в `replacing`;
     - наблюдатель (`childList`): в одной пачке записей добавленный элемент, чей id совпадает с id удалённого, — это замена. Так ловятся замены из JS без htmx.

     Множество очищается на `htmx:afterSettle` этого запроса и на следующем кадре после пачки наблюдателя. Элемент, чей id есть в `replacing`, появления не проигрывает, и на нём сразу ставится `data-motion-done` (атрибуты `data-*` htmx при settle не трогает). **Сравнение «было — стало» делается на `htmx:afterSettle`, а не на `afterSwap`.** До settle новая строка несёт старые `class` и `style` (§3, перенос атрибутов). «Было» берётся из снимка старого элемента на `oobBeforeSwap` или `beforeSwap`. Сравнение на `afterSettle` ведёт только два вида пресетов: счётчики (§6.4.6) и `ai-ready` (п. 8). Звезду, прочитано и архив оно не анимирует: у них один владелец, доменное событие (§6.4.4). Сюда же относится `afterSwap` на элементе, у которого `event.target !== detail.target`, а id совпадает с id `detail.target` (основной `outerHTML` с тем же id, например опрос `row_poll`).
  5. **OOB-свапы никогда не проигрывают появление.** **Решение планировщика.** Сегодня все они — обновления или `delete` (§3). Новый элемент из OOB без пары по id (такого сейчас нет) тоже не анимируется. Если появится OOB, который действительно добавляет контент, его объявят отдельно, в регистре.
  6. **Пара путей не даёт двойного запуска.** `afterSwap` срабатывает синхронно внутри свапа, а записи наблюдателя приходят позже, микрозадачей. Узел, который обработал путь htmx, попадает в `WeakSet` обработанных, и наблюдатель его пропускает. Узлы с классом `htmx-added` (htmx ставит его на новый контент до settle) наблюдатель тоже оставляет пути htmx.
  7. Каждый новый элемент проигрывает появление один раз (`data-motion-done`, как сейчас). Для контейнера-цели метка ставится на новых детях, а не на самом контейнере.
  8. **ИИ-блок пришёл готовым.** **Решение планировщика.** Это явный пресет состояния, а не появление. Опрос `ai_spinner` (`ai_blocks.html:33`, `hx-trigger="every 5s"`, `hx-swap="outerHTML"`) заменяет себя на готовый блок с тем же id: `ai-summary-{id}` и `ai-context-{id}` (`routers/web/app/ai.py:211, 253, 293`). По правилам 2 и 4 появления здесь нет. Регистр задаёт для этих id правило `ai-ready`: если снимок старого элемента на `beforeSwap` был заглушкой опроса (`[hx-trigger*="every"]` или `.ai-loading-indicator`), а новый элемент на `afterSettle` — нет, проиграть `fade-up`. Новый элемент проверяется после settle, потому что до него он несёт старый `class` (§3). Строка инвентаря §7 ссылается на это правило.
- **Свап внутри View Transition.** Если свап идёт с переходом (§6.6), анимацией служит сам переход. Появление внутри цели в этот раз не играется, иначе анимация будет двойной. Слой знает это заранее: он сам ставит override на `htmx:beforeSwap` и видит неотменённый `htmx:beforeTransition` для этой цели.
- **Цель появления в статье.** **Решение планировщика.** В `#article-detail` и в `#inline-article-detail-content` `fade-up` и `fade-up-short` играются на элементе `<article>` (`article_detail.html:121-257`), а не на обёртке. Рядом с ним, вне `<article>`, в том же свапе лежит модалка чата `fixed inset-0` (`article_detail.html:260-261`). У предка с `translate` фиксированный потомок привязался бы к предку, а не к окну.
- **Видимость.** Анимируются только элементы в окне просмотра (проверка по `getBoundingClientRect` против прямоугольника прокручиваемого родителя). Невидимые сразу получают `data-motion-done`.

#### 6.4.2 Выход (удаление и скрытие без задержки ввода)

Принцип: **изменение состояния не ждёт анимации.** Модуль удаляет или скрывает элемент сразу, как и сейчас. Удалённый элемент исчезает мгновенно. Отклик дают соседи, которые подъезжают на освободившееся место (FLIP), и CSS-выход оверлеев. Копий удалённого («призраков») нет. **Решение планировщика.**

Три вида выхода:

1. **Оверлеи Basecoat (диалог, палитра, меню, поповер, тост)** выходят через собственный CSS (`allow-discrete`, `data-closing`, `aria-hidden`), перенастроенный на наши токены. Добавляются три правила в `motion.css`:
   - закрывающийся оверлей сразу перестаёт ловить указатель: `:is(.dialog, .alert-dialog, .command-dialog, .drawer):not([open]), .drawer[data-closing], [data-popover][aria-hidden='true'], .toaster .toast[aria-hidden='true'] { pointer-events: none; }`;
   - длительность выхода: диалог, палитра и меню — `--t-fast` с `--rf-ease-in`; тост — `--t-fast-max`;
   - переходы остаются конечными и ненулевыми (минимум 0,01 мс даже под reduced motion), потому что тостер удаляет узел, а поповер переводит фокус на `[autofocus]` по `transitionend` (`popover.min.js`, `toast.min.js`). Поэтому ни одно правило reduced motion не ставит `transition: none` на оверлей, в том числе через `[data-motion]` (§6.11).
2. **Лист (drawer) и его задержка 550 мс.** **Решение планировщика:** `ui/dialog.js`, который уже владеет открытием и закрытием листов (`dialog.js:1-33, 58-64`), после `basecoat:initialized` заменяет у каждого `.drawer` метод `close` на нативный `HTMLDialogElement.prototype.close`. Вендорный файл не меняется. Лист сразу перестаёт быть модальным, `inert` с остальной страницы снимается. Видимый выход делает CSS: в `motion.css` правило для `.drawer:not([open])` с `transition-behavior: allow-discrete` на `display` и `overlay`, длительность `--t-fast-max`. Escape и клик по фону идут через переопределённый `close()` (Basecoat вызывает `t.close()` в обработчике `cancel` и `pointerup`), поэтому тоже становятся мгновенными. Это меняет `dialog.js`, а не модули: это проводка оверлеев, которой `dialog.js` уже владеет. Нужен e2e-тест: «закрыть лист и кликнуть по странице позади через 30 мс — клик доходит».
3. **Строки и блоки, которые убирает JS или htmx: FLIP соседей.** Сюда входят `savedArticleRemoved` → `row.remove()` (`app.js:710`), отложенное удаление → `hidden` (`pending.js:129`), закрытие inline-статьи (`app.js:3015-3020`), свёртка истории (`app.js:1477`), OOB `delete` чипа подсказки релевантности (`settings/_relevance_suggestion_applied.html`). FLIP-контейнеры: `#article-list` (из регистра, шаблон снимка не меняется), таблицы и списки отложенного удаления (источники, метки, фильтры) и ряд чипов в `settings/_relevance_suggestions.html` (через `data-motion-flip`; эти шаблоны вне снимка). Схема:
   - **Снимок прямоугольников у причины.** Слой подписан в фазе capture на причины удаления двух видов (**решение планировщика**):
     - **синхронные:** доверенный `click`, `keydown`, `pointerup` и доменные события (`savedArticleRemoved`, `rf:markedall`). Такой снимок покрывает только удаление или скрытие, которое модуль делает синхронно в той же задаче: `hidden` из `pending.js`, `row.remove()` по `savedArticleRemoved`, закрытие inline-статьи, свёртка истории. Удаление, которое придёт позже с ответом сервера, этот снимок не ждёт: на следующем кадре он отбрасывается;
     - **серверные:** `htmx:beforeSwap` и `htmx:oobBeforeSwap` — только у запросов, **не** помеченных как опрос (та же пометка на `htmx:configRequest`, что в §6.4.1, правило 2). Так снимок получает OOB `delete` чипа релевантности и любое удаление, которое приходит в ответе на действие пользователя. Снимок живёт до `htmx:afterSettle` этого запроса.

     Capture-подписки слоя срабатывают раньше всплывающих обработчиков `app.js` и `ui/*`, в том числе `pending.js:351`, при любом порядке загрузки (§3). В этот момент слой записывает `getBoundingClientRect()` видимых детей ближайшего FLIP-контейнера в затронутой области: цель свапа, строка с ключом удаления под `[data-rf-delete]`, строка статьи из события. Пишутся только прямоугольники, не больше 40, без клонов и вычисленных стилей.
   - **Следствие.** Модуль удаляет или скрывает, как сегодня. MutationObserver слоя (`childList`, атрибут `hidden` и токен `hidden` в `class` по правилу §6.4.1) подтверждает, что ребёнок FLIP-контейнера ушёл или скрылся.
   - **Полёт.** В том же обработчике наблюдателя (микрозадача после изменения, до отрисовки) слой читает новые прямоугольники записанных соседей. Каждый, кто сдвинулся, проигрывает `flip`: `translate` от разницы «было минус стало» к покою за `--t-fast-max`. Анимируются не больше 10 видимых соседей, остальные стоят на месте. Неподтверждённые снимки отбрасываются: синхронные на следующем кадре (удаление не случилось, например пользователь отменил подтверждение), серверные на `htmx:afterSettle` своего запроса.
   - **Замена — не удаление** (то же правило id, что в §6.4.1, п. 4). Если в документе уже подключён элемент с тем же id или id есть в `replacing`, FLIP не играется. Обновление строки через OOB (`row_poll`, ответы на звезду и «прочитано», офлайн-воркер) соседей не двигает, по какому бы пути оно ни пришло.
   - **Целый контейнер.** Если удаление — часть свапа всей цели (`#article-list` при смене вида), FLIP нет: это навигация, у неё свой `list-enter`.
   - **Удаление от опроса** (OOB `delete` или свап в ответе на запрос с пометкой опроса): `beforeSwap` и `oobBeforeSwap` такого запроса снимка не делают, элемент исчезает без FLIP.
   - Рассматривал `anime.createLayout`, это готовый FLIP в anime 4.5. Отказался: он работает на JS-движке, пишет inline `transform` и глушит переходы через inline `transition: none !important`, а снимок до изменения ему тоже нужен. Свой FLIP на `anime.waapi.animate` — это десяток строк.
- **Мгновенный выход без отклика** (ничего не подъезжает): модалка поиска (`#search-modal-overlay`, класс `hidden`), подложка телефонного листа, очистка чата ассистента при смене области, удаление ошибки чата (`assistant.js:78`). Новое содержимое, которое приходит следом, получает обычное появление.
- **`#rf-motion-layer` — только для частиц звезды** (§6.4.4, вопрос владельца 1). Его создаёт `motion.js` при первой надобности: `position: fixed; inset: 0; pointer-events: none`, `aria-hidden="true"`, `inert`, z-index выше контента и ниже оверлеев верхнего слоя (строитель выбирает между z-index телефонного листа 30, статьи 40 и баннера 50, `base.html:250-315`). В слое только `<span>` частиц без id и без атрибутов `data-*`, `hx-*`, `aria-*`. Слой лежит вне `#article-list` и любых списков, поэтому `_kbRows()` (`app.js:2224-2227`), подсчёт видимых строк в `pending.js` и любые запросы по контейнеру его не видят. **Перекрытие:** частицы рисуются, только если `document.elementFromPoint` в центре звезды попадает в саму кнопку звезды или в её потомка. Звезда под полноэкранной статьёй (z 40, `base.html:309-315`), под листом сайдбара (z 30) или под диалогом частиц не получает, а пружинный поп кнопки остаётся. Частицы удаляются в `onComplete`, страховка — таймер `--t-med-max` + 100 мс. Если владелец откажется от частиц, слой не создаётся вовсе.

#### 6.4.3 Нажатие (press)

- Один делегированный `pointerdown` на `document` (capture, `passive: true`). Слушателей `pointerup`, `pointercancel` и `pointerleave` у нажатия нет. Цель: `closest('button, a[href], [role=button], [role=menuitem], [role=menuitemradio], [role=menuitemcheckbox], [role=tab], [role=option], summary, label.switch, [data-rf-open], [data-rf-nav], [hx-get]:not([hx-trigger]), [hx-post]:not([hx-trigger]), [hx-trigger="click"]')`. Голые `[hx-get]` не годятся: `<aside id="sidebar" hx-get hx-trigger="load, sidebarRefresh …">` (`main.html:298-304`) и контейнеры опроса тоже `hx-get`, и нажатие на пустое место сайдбара сжало бы весь сайдбар. Ряды сайдбара — это `<a hx-get>` без `hx-trigger` (`sidebar.html:44`), строки списка — `hx-trigger="click"` (`article_row.html:309`), они попадают.
- Не нажимаются: `disabled`, `[aria-disabled=true]`, `[data-motion-press=off]`, строка в состоянии свайпа (`[data-rf-swipe]`), поля ввода, элементы внутри `#rf-motion-layer`, а также элементы с вычисленным `display: inline`. На строчной незамещаемой ссылке в тексте свойство `scale` не действует, у таких ссылок отклик даёт CSS-ховер.
- Строки списка (`.article-row`), ряды сайдбара и строки таблиц получают `press-soft`: определяются по селектору в регистре, атрибут в шаблонах снимка не нужен.
- Клавиатура: Enter или пробел на сфокусированной кнопке проигрывает одно короткое нажатие на `keydown` (без повтора на `e.repeat`). j/k нажатия не дают: у них свой отклик (§6.4.4).
- **Форма нажатия.** **Решение планировщика** (вариант (a) из второй проверки дизайна, ревизия 4). На `pointerdown` (и на `keydown` для клавиатуры) идёт **один** вызов `anime.waapi.animate` «запустил и забыл»: `scale: [1, ~0,94, покой]` (у `press-soft` — `[1, ~0,985, покой]`), `ease` — пружина `press` из `springEase('press')`, длительность ≤ `--t-fast-max`. Удержания нет: кнопка не стоит вдавленной, пока палец лежит, и `pointerup`, `pointercancel`, `pointerleave` ничего не запускают и не останавливают. Анимация кончается сама и чистится по правилу 1. В anime 4.5.0 `ease` — это `easing` всего эффекта, а не отдельного отрезка (прочитано в `anime.umd.min.js`: `easing` в словаре тайминга каждой нативной анимации). Поэтому одна пружина ведёт оба отрезка: нырок приходится на начало, а перелёт пружины выше 1 продлевает последний отрезок за покой, и кнопка чуть «подпрыгивает» перед остановкой. Это и есть «живой» отклик. Последняя точка `linear()` равна 1, так что последний кадр — покой (§6.1, правило 3). Точная глубина нырка и параметры пружины — за строителем в рамках §6.3. Второе быстрое нажатие на ту же кнопку сначала останавливает первое (§6.1, правило 3) и начинает своё с `1`.
- Нажатие идёт через свойство `scale` и `anime.waapi.animate` (§6.1), поэтому не спорит с inline `transform` свайпа. Пока оно идёт, `transition-all` Basecoat на `.btn` не срабатывает.
- **Известный остаток.** На элементах с `transition-all` (`.btn`, `.tabs`, `.switch`) после `revert()` браузер запускает CSS-переход `scale` от зафиксированного `1` к покоящемуся `none`. Проба: `transitionrun` для `scale` срабатывает при любом последнем кадре: `1`, `none` или вычисленное значение. Визуально это ничего не меняет: `none` и `1` — один и тот же масштаб. Но такой переход виден в `getAnimations()`. То же, скорее всего, бывает с `translate` (FLIP, `revert`, `attention`, `swipe-snap`): фиксация может записать `0px` против вычисленного `none`, и на чипах с `transition-all` (чипы релевантности получают FLIP) появится тождественный переход `translate`. Пробой это не проверено. Помощники e2e (`runningAnimations`) и `idle()` не считают **тождественные** `CSSTransition` по `scale` и по `translate`: у которых начало и конец оба равны покою (`1`/`none` для `scale`, `0px`/`none` для `translate`). **Решение планировщика:** принять. Если строитель увидит от них вред (лишний `transitionend` у кого-то из слушателей), `motion.css` убирает `scale` и `translate` из `transition-property` у `.btn`, `.tabs`, `.switch` и чипов с `transition-all`.
- Нажатие никогда не вызывает `preventDefault` и не ждёт: клик проходит как обычно.

#### 6.4.4 Смена состояния

- **Один владелец на пару «статья и состояние».** **Решение планировщика.** Звезду, прочитано и архив анимирует только путь доменного события (`articleStarChanged`, `articleReadChanged`, `articleArchiveChanged`). Сравнение на `afterSettle` (§6.4.1, п. 4) и наблюдатель эти состояния не анимируют, даже если OOB-ответ перерисовал кнопку, которую оптимистичное обновление пропустило (звезда участника истории, звезда в заголовке). Повторы гасит память слоя: `Map` «id статьи → последнее показанное значение» для каждого из трёх состояний. Анимация играется, только если новое значение отличается от запомненного. Таймеров дедупликации нет.
- **Звезда** (`articleStarChanged`). Обработчик слоя стоит в фазе capture на `document` и поэтому срабатывает раньше обработчика `app.js` (`app.js:2631`, §3). Если статьи ещё нет в памяти, слой берёт прежнее значение из DOM так же, как `_starIsStarred` (`app.js:2718-2723`): глиф ★ или `fill` у svg. Если значение действительно сменилось, слой ставит анимацию в микрозадачу, то есть после того, как `app.js` перерисует кнопку. Подтверждение сервера с тем же значением ничего не проигрывает. Откат после ошибки (`htmx:responseError`/`sendError` на элементе-звезде, `app.js:2752-2753`) проигрывает `revert` вместо `star-off`. Цели: все кнопки звезды этой статьи (строка, нижняя панель, меню заголовка), найденные по тем же хукам, что в `app.js:2706-2716`. `star-on` с пиком 1,2 может на миг показать полосу прокрутки в контейнере `overflow: auto`, потому что `scale` входит в прокручиваемую область. Если строитель это увидит, пик опускается до 1,15.
- **Прочитано** (`articleReadChanged`, плюс автоотметка при прокрутке через то же событие). `read-dot` на индикаторе непрочитанного в строке. Прозрачность строки по-прежнему ведёт CSS (`base.html:140`), слой её не трогает.
- **Архив** (`articleArchiveChanged`). `pop` на индикаторе архива строки (`[data-archived-indicator]`, `app.js:2785-2787`) и на кнопке. Строку архив из списка не убирает: `app.js:2759-2789` только переключает индикатор, а `read.js:148` показывает тост. Поэтому FLIP у архива нет.
- **Прочитать всё** (`rf:markedall`, `count > 0`). `mark-all-wave` по видимым непрочитанным строкам, затем `count-pop` на счётчиках. Если список сразу перерисовывается, волна просто обрывается вместе со старыми строками: она чисто визуальная.
- **Настройка сохранена** (`rf:settingsaved` на `<body>`, его отправляет `ui/settings.js:101`). `confirm` на элементе с `name=<field>`. Список терминов релевантности, сохранённый кликом по подсказке, получает `confirm` на событие `relevance-terms-saved` (уже есть, `HX-Trigger`).
- **Откат настройки.** `RFSettings.restore()` (`ui/settings.js:63-68`, вызовы на `:116` и `:146`) меняет `checked`/`value` как свойство. Атрибут не меняется, и наблюдатель этого не видит. **Решение планировщика:** `ui/settings.js` в `restore()` отправляет на `<body>` доменное событие `rf:settingreverted` `{field}`, тем же способом, что и `rf:settingsaved`. Это событие, а не вызов анимации. Слой проигрывает `attention` на элементе с `name=<field>`. Событие записывается в DOM-контракт.
- **Ошибка формы** (свап с `aria-invalid` или `data-field-error`, ответ `422`). `attention` на поле и `fade-up-short` на тексте ошибки.
- **Активный пункт навигации.** Смену `.active` у ряда сайдбара и `aria-current` у вкладок показывает CSS-переход цвета фона `--t-fast`. Слой даёт `press-soft` в момент клика.
- **Открытая статья при j/k.** Перехода нет (§6.6.2). `<article>` новой статьи получает `fade-up-short` (`--t-fast`, 4px), строка курсора — короткую вспышку фона. Так же на телефоне, когда статья сменяется внутри уже открытого полного экрана: кнопка «Next» (`app.js:3757-3767`) или новая статья из ленты (ветка `replaceState` на `app.js:3518`).
- **Занят** (`htmx:beforeRequest` на кнопке): `busy-in` для `htmx-indicator` и спиннеров внутри кнопки, с задержкой 150 мс.

#### 6.4.5 Жесты

- **Свайп строки** (`ui/read.js:220-300`). Поведение пальца не меняется: строка следует за пальцем через inline `transform` без анимации. Меняются три вещи:
  1. Возврат строки (`snapBack`, `read.js:248-262`) становится пресетом `swipe-snap`. `read.js` вместо прямого `RFMotion.animate` сначала сам очищает строку (`clearRow`: снимает `data-rf-swipe` и inline `transform`, конечное состояние сразу), затем вызывает `RFMotion.play('swipe-snap', row, {from: dx})`. Пресет анимирует свойство `translate` от `dx px 0` к покою с пружиной `snap`. Первый кадр применяется в том же задании, поэтому строка не прыгает. `revert()` восстанавливает только `translate` и `transform` свайпа не трогает (проба, §3). Это один из двух прямых вызовов из модулей в §4, и он переводится на имя пресета.
  2. Когда палец проходит порог фиксации, на смену `data-rf-swipe` слой проигрывает `swipe-commit` (пульс края цвета действия). Видимость края уже есть в `input.css:736-737`.
  3. Сама фиксация (звезда или прочитано) проходит через обычный клик или запрос, поэтому отклик даёт пресет состояния.
  - Новый `pointerdown` на строке, у которой идёт `swipe-snap`, останавливает его: capture-слушатель слоя вызывает `handle.stop()` раньше обработчика `read.js` (§6.1, правило 5). Палец сразу владеет `transform`, и `translate` пресета не складывается с ним.
- **Долгое нажатие на ряд сайдбара** (`ui/shell.js:299-340`). `pop` на кнопке «прочитать», когда она появляется (`touch-active`).
- **Ресайзер списка** (`main.html:316-318`). Не анимируется: им управляет мышь.

### 6.6 View Transitions

- **Навигация между экранами — это полная загрузка документа.** У `<body>` нет `hx-boost` (`base.html:586`). Сайдбар, вкладки телефона, подменю настроек (`settings/base.html:47`), ссылки в Sources и Assistant — обычные `<a href>`. `hx-boost` стоит только на формах. Поэтому переход между экранами — **кросс-документный View Transition**, только CSS. В `motion.css` добавляется:
  ```css
  @media (prefers-reduced-motion: no-preference) {
    @view-transition { navigation: auto; }
  }
  ```
  Переход ограничен уже существующим правилом `::view-transition-*(*) { animation-duration: var(--t-fast-max) }` (`motion.css:5-10`). Анимация — стандартное перекрёстное затухание. Оболочка (сайдбар, вкладки телефона) получает `view-transition-name`, чтобы не мигать. Эти имена действуют только при кросс-документной навигации: под `html[data-rf-vt]` они снимаются, и в переходах внутри документа участвуют только корень и `rf-detail` (§6.6.2). Браузеры без поддержки (старый WebKit, Firefox) просто загружают страницу. Работает и для страниц, которые отдаёт офлайн-воркер: это та же навигация того же источника. Публичные страницы, приветствие (`app/welcome.html`, `welcome_feeds.html`) и share target (`app/share_target.html`) — тоже полные документы и получают тот же переход. **Решение планировщика:** включить кросс-документный переход в этапе 1, потому что это одно CSS-правило на всё приложение.
- **Переход внутри читалки.**
  - **Смена вида** (клик по ряду сайдбара → свап `#article-list`, `sidebar.html:44-201`): не View Transition, а `list-enter` (§6.4.1). Переход на смене списка снимал бы всю страницу ради одного столбца, а каскад даёт больше отклика. **Решение планировщика.**
  - **Открытие статьи в трёх колонках** (клик по строке, `article_row.html:308-311`, свап `#article-detail`) — §6.6.2.
  - **Inline-статья** (2 колонки и телефон в inline-режиме, `app.js:3063-3110`). Запрос отменяется, контейнер строит JS. Перехода нет. `<article>` внутри `#inline-article-detail-content` получает `fade-up` после `afterSettle`, строка — `press-soft`.
  - **Полноэкранная статья на телефоне, оверлей истории и оверлей глубокой ссылки** (`mobile-detail-open`, `story-detail-open`, `deeplink-detail-open`) — §6.6.1.
  - **Свап в `#article-detail` без перехода** (j/k, переход отменён, «Next» на телефоне, ответ, пришедший в уже поднятый оверлей истории): `fade-up-short` на новом `<article>`, если панель видна. Если панель скрыта (телефон до открытия полного экрана), анимации нет по правилу видимости (§6.4.1).

**Помощник и правила.** **Решение планировщика.**

- В `app.js` один помощник: `_shellTransition(key, fn)`. Он вызывает `RFMotion.transition(fn, {key, scope})`, если слой есть, иначе `fn()` сразу. `scope` выводится из суффикса ключа: `:on` → `shell-open`, `:off` → `shell-close`. Шесть мест из таблицы вызывают только его.
- **Отложенное обновление.** `startViewTransition` вызывает `fn` не сразу, а после снимка старого состояния, то есть примерно через кадр. До этого класс ещё старый. Под reduced motion и без API `RFMotion.transition` вызывает `fn` синхронно, как сейчас (`motion.js:351-353`).
- **Один переход на действие: склейка по ключу.** Пока у текущего перехода `fn` ещё не вызван, повторный вызов с **тем же** `key` не запускает новый переход и не вызывает свой `fn`, а возвращает текущий handle. Пример: «Назад» (место 2 или 5) запускает переход и сразу зовёт `history.back()`. `popstate` может прийти раньше, чем отработал `fn`. Тогда класс ещё стоит, и обработчик (место 3 или 5 через `:1430`) вызывает помощник с тем же ключом. Вызов склеивается, поэтому нет второго перехода и второго `_dwellSend`. Если `popstate` пришёл после `fn`, класс уже снят: место 3 не видит смены, а место 5 возвращает `false`. Вызов с другим ключом во время отложенного обновления сначала синхронно выполняет отложенный `fn`, затем пропускает старый переход и запускает новый.
- **Сброс отложенного обновления.** `fn` оборачивается защитой «один раз». Слой выполняет отложенный `fn` синхронно и пропускает переход (`skipTransition`) в двух случаях: на `htmx:beforeSwap` (capture) и на `keydown` (capture). Поэтому обработчики свапа (`_syncBottomBar` на `afterSettle`, ветка `app.js:3517`) и клавиатура (`_kbRows`, `app.js:2213-2218`) всегда видят актуальный класс. Остальные читатели из списка выше срабатывают от действий пользователя, которые приходят позже кадра. Цена: если ответ пришёл быстрее кадра, этот переход пропускается.
- **Двойного перехода при открытии на телефоне нет.** Слой ставит override с `transition:true` только в трёх колонках (§6.6.2). Свап статьи на телефоне идёт без перехода (панель ещё скрыта), а единственный переход даёт место 1.
- **Оверлей истории (место 4).** Класс ставится сразу после `htmx.ajax`, до ответа. Переход поднимает панель справа, пустую или с прошлым содержимым (её очищает `_closeStoryOverlay`). Когда приходит ответ, свап в уже видимую панель проигрывает `fade-up-short` (список выше). Получается один переход и одно появление на одно действие.
- **Анимация.** Открытие: снимок `rf-detail` въезжает справа (`translate` 16px → 0 и `opacity`). Закрытие: уезжает вправо. Корень не анимируется, анимация укладывается в 165 мс (§6.6.2).

  - раскладка — три колонки (`html[data-layout="3"]`, бакет не `small`);
  - нет reduced motion, вкладка видима;
  - браузер умеет `document.startViewTransition`. Без API htmx всё равно шлёт `htmx:beforeTransition`: событие идёт до проверки API. Без этого условия слой подавил бы появление, а перехода бы не было. Без API свап идёт обычным путём и получает `fade-up-short` (§6.6);
  - запрос начат доверенным кликом: `triggeringEvent.isTrusted` из `htmx:configRequest`. Клик из `_kbOpenRow` (`row.click()`, `app.js:2240-2245`, j/k) недоверенный. `htmx.ajax` из `_openStoryMember` проверяется по последнему доверенному `pointerdown` или `click` слоя на `[data-open-story-member]`;
  - прошлое открытие было больше 300 мс назад. Время открытия ставит **обёртка** `startViewTransition` (ниже, шаг 1) в момент, когда переход со scope `detail` действительно стартует, а не тот, кто ставит override. И эта проверка, и вето на `beforeTransition` сравнивают текущее время с этой **прошлой** меткой, поэтому запрос не накладывает вето сам на себя.

  Значение override — **полная действующая спецификация** плюс модификаторы: `(detail.swapOverride || наследуемый hx-swap элемента запроса || htmx.config.defaultSwapStyle) + ' transition:true'`, если в ней ещё нет `transition:`, и `+ ' settle:0ms'`, если в ней нет `settle:`. «Наследуемый» значит то же, что у htmx (`re(elt, "hx-swap")`, §3): ближайший `hx-swap` у элемента или предков. Так сохраняются `HX-Reswap`, swap из `htmx.ajax(…, {swap})` и модификаторы строки, потому что `gn()` не сливает override с `hx-swap` (§3). `settle:0ms` убирает задержку settle в 20 мс изнутри колбэка обновления: пока он не завершился, браузер держит отрисовку на старом снимке (§3). Шаблоны снимка не меняются, переход работает и для фрагментов офлайн-воркера: это тот же `beforeSwap`. **Решение планировщика.**
- **Вето на `htmx:beforeTransition`** остаётся второй линией защиты с теми же условиями: reduced motion, не три колонки, недоверенный запуск, меньше 300 мс, вкладка скрыта, нет API. Если вето не случилось, обработчик только запоминает `pendingScope = 'detail'`. Атрибут ставит обёртка (ниже).
- **Обёртка `document.startViewTransition`.** **Решение планировщика.** Заменяет опрос `document.getAnimations()` и таймер-страховку ревизии 2. `motion.js` при загрузке, если API есть, один раз ставит на `document` собственное свойство `startViewTransition`. Вызывающие (htmx, `RFMotion.transition`) берут его в момент вызова и попадают в обёртку. Обёртка:
  1. если есть `pendingScope`, ставит `html[data-rf-vt]` в это значение **до** вызова оригинала (снимок старого состояния браузер делает позже, на шаге отрисовки) и сбрасывает `pendingScope`. Если scope — `detail`, здесь же записывает время открытия для вето 300 мс;
  2. вызывает оригинал с `document` в роли `this` и теми же аргументами (колбэк или объект `{update, types}`);
  3. запоминает **каждый** переход, который видит, как `current`, с `pendingScope` или без. Для каждого по `vt.finished.then(clear, clear)` снимает атрибут, **только если `current` всё ещё этот переход**. Пропущенный переход не снимает атрибут, который только что поставил его преемник. `finished` отклоняется, если htmx отклонил промис обновления (ошибка свапа), поэтому снятие идёт по обоим исходам;
  4. если оригинал бросил исключение, снимает атрибут и сам синхронно вызывает колбэк обновления: свап htmx не теряется.

  Пустые и пропущенные случаи. Вкладка скрыта или начался новый переход: браузер пропускает текущий, колбэк всё равно выполняется, `finished` разрешается, атрибут снимается или остаётся за преемником по п. 3. Колбэк завис: Chrome прерывает его по своему тайм-ауту, `finished` отклоняется, атрибут снимается. `pendingScope` дополнительно сбрасывается на `htmx:afterSettle` и `htmx:swapError`, чтобы он не утёк в чужой вызов. Переход без `pendingScope` (никто из наших путей его не заказывал) обёртка пропускает как есть: атрибут не ставит, но запоминает как `current` и вешает то же снятие по `finished` (п. 3). Если такой переход пропустит scoped-переход, атрибут снимется по его `finished`, а не останется до следующего scoped-перехода. Сегодня таких переходов нет (`transition:true` и `globalViewTransitions` в шаблонах и JS не встречаются), правило — на будущее. `RFMotion.idle()` ждёт `current.finished`. `RFMotion.transition` ставит `pendingScope = opts.scope` и вызывает тот же `document.startViewTransition`, так что путь один. Повторный переход во время идущего браузер пропускает сам: новый `startViewTransition` пропускает текущий.
- **Граница CSS: атрибут `html[data-rf-vt]`.** Правила перехода внутри документа действуют только под этим атрибутом, поэтому кросс-документный переход их не видит. **Решение планировщика.**
  - Значения: `detail` (переход htmx в трёх колонках), `shell-open` и `shell-close` (§6.6.1).
  - Ставит и снимает только обёртка (выше). Новый переход перезаписывает значение.
  - В `motion.css`, по смыслу:
    ```css
    html[data-rf-vt] #article-detail { view-transition-name: rf-detail; }
    /* имена оболочки для кросс-документного перехода (§6.6) здесь снимаются:
       иначе #tab-bar, который скрыт под полноэкранными классами
       (mobile_bars.html:60), получил бы свой выход и вход */
    html[data-rf-vt] :is(<элементы оболочки с view-transition-name>) { view-transition-name: none; }
    /* корень сразу показывает новое состояние, без анимации */
    html[data-rf-vt]::view-transition-group(root),
    html[data-rf-vt]::view-transition-old(root),
    html[data-rf-vt]::view-transition-new(root) { animation: none; }
    html[data-rf-vt="shell-open"]::view-transition-new(rf-detail) { /* въезд справа */ }
    html[data-rf-vt="shell-close"]::view-transition-old(rf-detail) { /* выезд вправо */ }
    ```
  - Атрибут ставит только `motion.js` во время работы страницы. В шаблонах его нет, это проверяет `check-motion-calls.mjs` (§9). Новый документ при кросс-документной навигации его не несёт. Его псевдоэлементы `::view-transition-*` получают обычное перекрёстное затухание корня из §6.6, а у `#article-detail` там нет имени. Публичные страницы `motion.js` не грузят.
  - `transform` на сам `#article-detail` не ставится: внутри у него фиксированные панели (`base.html:309-315`). Анимируются только снимки-псевдоэлементы.
- **Пауза ввода.** Анимация `rf-detail` длится не больше `--t-fast-max` (165 мс). Полная пауза отрисовки — это снимок старого состояния, колбэк обновления (свап и, благодаря `settle:0ms`, сразу settle), снимок нового и анимация, то есть 165 мс плюс несколько кадров. e2e мягко меряет время от вызова обёртки до `finished`: не больше 250 мс (§9, e2e 3).

### 6.7 Офлайн и рендер на клиенте

- **Фрагменты от воркера идут через htmx.** Воркер отвечает на htmx-запросы снимком, `overlay.js` подставляет состояние на `htmx:beforeSwap` (`overlay.js:7-11`), а `afterSwap` срабатывает как обычно. Появление, счётчики, звезда и волна работают офлайн без отдельного кода. События `articleStarChanged`, `articleReadChanged`, `rf:markedall` воркер тоже шлёт (`offline/router.js:323, 450, 554`).
- **Что строит JS на странице, и чем это покрыто:**
  - inline-оболочка статьи (`app.js:3082-3101`) — §6.6;
  - тосты (`ui/toast.js`) — §6.5;
  - офлайн-баннер и модалка выхода (`page.js:693-704, 1080`) — §6.5;
  - скелет списка (`read.js:168-207`) — `fade-up-short` на слое скелета через наблюдатель `childList` на `#article-list` с фильтром `.article-list-loading`; скелет и так появляется с задержкой 150 мс;
  - сообщения чата ассистента (`assistant.js`) — этап 4;
  - пустое состояние после удаления из «Сохранённых» (`app.js:722-724`) — `fade-up`.
- **Вне охвата:** `offlinePage` и `launch.js` (§2).
- **Цена `data-motion` в шаблонах снимка.** Атрибут в `article_row.html`, `article_detail.html`, их include и в `sidebar.html` (у сайдбара есть офлайн-зеркало и golden-файлы `tests/fixtures/offline_drift/sidebar-*.html`) значит: правка зеркала в `templates.js`, перегенерация golden-файлов, повышение `OFFLINE_TEMPLATE_VERSION` с новым хешем и запись в DOM-контракте. **Решение планировщика:** пресеты для этих мест привязываются к существующим хукам через регистр в `motion.js` (в том числе `#article-list` как FLIP-контейнер и `<article>` как цель появления), и атрибуты туда не добавляются. **Ни один этап не правит снимок**: переход при открытии статьи включается через `detail.swapOverride`, а намерение объявлено на `#article-detail` в `main.html` (§6.6.2). Повышения `OFFLINE_TEMPLATE_VERSION` в этой работе нет. Если строитель всё же найдёт неизбежную правку снимка, это отдельный вопрос к планировщику до правки: правка идёт вместе с зеркалом, golden-файлами и повышением версии, одним коммитом.
- **Shell cache.** Если появится `motion-presets.js`, он подключается статическим тегом. `sync.js` найдёт его сам. Офлайн-e2e проверяет оболочку после каждого этапа.

### 6.8 Двойная анимация: правила

1. Пока WAAPI-пресет идёт, CSS-переход того же свойства не срабатывает: WAAPI не трогает inline-стиль. После конца переход не срабатывает, если последний кадр равен покоящемуся значению (§6.1, правило 3). Единственный остаток — невидимые тождественные переходы `scale` (`1 → none`) и, вероятно, `translate` (`0px → none`) на элементах с `transition-all` (§6.4.3).
2. Где у Basecoat уже есть открывающий переход на то же свойство (панель диалога, палитры, листа; тост), `motion.css` снимает это свойство из перехода для открытого состояния помеченных элементов. Выход остаётся за CSS.
3. Прозрачность строки списка ведёт только CSS (`base.html:140`). Ни один пресет не трогает `opacity` у `.article-row`, кроме появления новой строки. Её последний кадр — покоящееся значение (0,75 для прочитанной), поэтому после очистки переход CSS не срабатывает (проба, §3).
4. Внутри свапа с View Transition появление не проигрывается (§6.4.1).
5. Одна смена состояния — один владелец анимации (§6.4.4, §6.4.6).
6. `.folder-just-moved` (`input.css:803`) мёртв, а `feeds-settings.js:60-68` дублирует вспышку через anime. Обе вспышки сводятся к одному пресету `flash` (CSS-класс `.rf-flash`, который сейчас не используется). Мёртвое правило удаляется. Для прямого вызова в `feeds-settings.js` есть два пути: слой сам слушает свап таблицы источников и сравнивает порядок папок, или `feeds-settings.js` вызывает `RFMotion.play('flash', row)` вместо нынешнего `RFMotion.animate`. **Решение планировщика:** второй путь. Модуль уже знает, какая папка переехала (`feeds-settings.js:55-57`), а слою пришлось бы восстанавливать это сравнением. Это второй и последний прямой вызов пресета из модуля.

### 6.9 Первая загрузка страницы

- При первой отрисовке документа появление **не играет** (как сейчас: `motion.js:11-13`). Иначе элемент мигнёт видимым и потом станет прозрачным (T17-R3). Исключения — пресеты без скрытого начального состояния, которые сообщают о результате отправки формы: `attention` на ошибке входа или регистрации (полная перезагрузка страницы), `flash`. Их слой запускает на `DOMContentLoaded` для элементов `[data-motion="attention"]`.
- Первую отрисовку экрана анимирует кросс-документный переход (§6.6).
- Список статей в читалке приходит свапом после загрузки (`main.html:309-313`, скелет, затем `_autoLoadArticleList`, `app.js:949-1010`). Это навигация, поэтому первый список получает `list-enter`. **Решение планировщика:** так задумано, потому что на экране до этого скелет, а не строки.
- Сайдбар тоже приходит свапом (`hx-trigger="load"`, `main.html:300`). Появления у него нет (§6.4.1), только попы счётчиков со второго свапа.

### 6.10 Производительность

- Только `opacity`, `transform`/`scale`/`translate`. Цвет — только через CSS-класс вспышки.
- Каскад: не больше 10 видимых элементов (§6.3). Список из 200 строк анимирует 10, остальные стоят на месте.
- FLIP: снимок — не больше 40 прямоугольников и только видимые; анимируются не больше 10 соседей.
- Частицы: 6 на одну звезду, не больше 2 вспышек одновременно.
- Счётчики: не больше 8 попов одновременно.
- Наблюдатели: один MutationObserver на `body` (`childList`, `subtree`, `attributes` с фильтром из четырёх атрибутов и `attributeOldValue`) и отдельный наблюдатель `characterData` только на элементах-счётчиках. Обработчик работает за O(число записей), проверяет только `nodeType === 1`, `hasAttribute` и регистр. Тяжёлую работу (кроме чтения прямоугольников FLIP, которому нужен момент до отрисовки) он откладывает в `requestAnimationFrame`. Свап всего `#article-list` распознаётся по флагу из `htmx:beforeSwap` и обрабатывается одним проходом, а не построчно.
- `will-change` не ставится заранее, только на время анимации (WAAPI делает это сам).
- Если вкладка скрыта (`document.hidden`), пресеты не запускаются.
- Бюджет: на списке из 200 строк смена вида не даёт длинной задачи (> 50 мс) от слоя (мягкая проверка в e2e через `PerformanceObserver('longtask')` в Chrome).

### 6.11 Reduced motion

- `RFMotion.reduced()` → пресеты не запускаются вовсе. **Без inline-конечных значений:** конечное состояние уже нарисовано сервером и CSS. Это меняет поведение только для пресетов. Сам `RFMotion.animate` до своего удаления в этапе 4 сохраняет контракт (`motion.js:292-305`).
- **Правило `[data-motion]` переписывается** (этап 1). **Решение планировщика.** Сейчас в `motion.css:31-35` стоит `[data-motion], .rf-flash { animation: none !important; transition: none !important; }`. Макросы этапа 3 ставят `data-motion="panel-in"` на диалоги, листы и палитру, а возможно, и на меню и поповеры (§6.5). Под reduced motion это правило побеждает, `transition` становится `none`, и `transitionend` больше не приходит: тостер не удалит узел, поповер не переведёт фокус. Новый вид:
  ```css
  @media (prefers-reduced-motion: reduce) {
    .rf-flash { animation: none !important; transition: none !important; }
    [data-motion] {
      animation: none !important;
      transition-duration: 0.01ms !important;
      transition-delay: 0s !important;
    }
  }
  ```
  `animation: none` на элементе с `data-motion` безопасен. Из ключевых кадров Basecoat есть вход тоста `toast-up`, он уже снят (`input.css:750-760`), и `dialog-scroll-lock` (`dialog.css:2-14`). Последний — анимация по шкале прокрутки на `html:has(... :modal)`: она держит место под полосу прокрутки, пока открыт модальный диалог. На `html` нет `data-motion`, поэтому правило её не трогает. Общий сброс §6.11 тоже не должен включать `html`. `animationend` никакой JS не ждёт: в `vendor/basecoat` его нет. Потомков правило не трогает, поэтому спиннеры продолжают крутиться. Тестов, которые закрепляют старое правило, нет: `tests/` его не проверяет, а `tests/js/motion.test.mjs` проверяет только разметку `data-motion`. Добавляется проверка (§9): ни одно правило reduced motion в `motion.css` и `input.css` не ставит `transition: none` на `[data-motion]`, `.toast`, `[data-popover]`, `.dialog`, `.drawer` или `.command-dialog`.
- `motion.css` получает общий сброс под reduced motion для компонентов Basecoat и оболочки: `.dialog, .alert-dialog, .command-dialog, .drawer, [data-popover], .toaster .toast, .sidebar, .tabs, .switch, .btn, #sidebar, #mobile-sidebar-backdrop` с потомками и `::backdrop` получают `transition-duration: 0.01ms !important`. Сами компоненты (без потомков) и `.toaster .toast` получают ещё `animation-duration: 0.01ms !important; animation-iteration-count: 1 !important`. Потомкам анимацию не режут, иначе остановится `animate-spin` внутри кнопки или диалога. Значение не `none`, потому что Basecoat ждёт `transitionend` (тостер, фокус поповера). Существующие правила `input.css:750-760` остаются или сливаются в этот блок.
- Исключения: спиннеры `animate-spin` и `chat-bounce` — это необходимые индикаторы состояния. `chat-bounce` под reduced motion уже заменён текстом (`assistant.js:217`). **Решение планировщика:** спиннеры оставить.
- View Transitions: кросс-документный переход объявлен только под `no-preference`. Внутри документа слой не ставит `swapOverride` с переходом и отменяет `htmx:beforeTransition`. `RFMotion.transition`, а значит и `_shellTransition`, уже работает без перехода: `fn` вызывается синхронно (`motion.js:351-353`). CSS-сброс `::view-transition-*` (`motion.css:24-29`) остаётся второй линией защиты.
- Если пользователь меняет настройку на лету: `reduced()` читается при каждом запуске, кэша нет (как сейчас).

### 6.12 Отказы и восстановление

- **anime.js не загрузился** (или в нём нет `waapi`) → ни один пресет не играется, слой ничего не пишет: состояние уже конечное. Обёртка `startViewTransition`, `RFMotion.transition` и `_shellTransition` от anime не зависят и работают как обычно.
- **`motion.js` не загрузился или упал** → нет ни одной анимации, приложение работает. Модули не зависят от слоя. Два прямых вызова (`read.js`, `feeds-settings.js`) проверяют `window.RFMotion && RFMotion.play`, как сейчас (`read.js:250-254`). Помощник `_shellTransition` в `app.js` тоже: без слоя `fn()` вызывается напрямую и синхронно, как до этой работы. Без слоя нет и обёртки, а htmx-переходов без override не бывает.
- **Переход пропущен, отклонён или упал** → атрибут `html[data-rf-vt]` снимается по `finished` (оба исхода) или остаётся за преемником (§6.6.2). Если упал сам вызов, обёртка выполняет обновление синхронно. Отложенное обновление оболочки выполняется самим браузером или сбросом слоя (§6.6.1). Состояние не теряется.
- **Ошибка внутри пресета** ловится в `try/catch` слоя и уходит в `setTimeout(throw)` (как `motion.js:300`). Если анимация уже создана, её останавливает `handle.stop()`, а чистит `onComplete → revert()`. Частицы убирает таймер-страховка.
- **View Transition не поддерживается** → обычный свап (как сейчас).
- **Свап во время анимации** → анимации старых узлов умирают вместе с ними. `activeCount` считает только подключённые цели.
- **Свайп во время пружины возврата** → новый `pointerdown` вызывает `handle.stop()` у `swipe-snap` (нативный `cancel()`, очистка через `onComplete`, §6.1, правило 5). Палец сразу владеет `transform`.
- **Обновление anime.js.** Правила очистки опираются на внутреннее поведение `WAAPIAnimation` 4.5.0 (фиксация, `revert()`, событие `cancel`). Это закрепляют e2e «Без следов» (§9, e2e 5). При обновлении anime они скажут, если поведение сменилось.

### 6.14 Инварианты

1. Под reduced motion ни один пресет не запускается, `RFMotion.activeCount()` всегда 0, слой не пишет inline-стилей, кросс-документного перехода нет.
2. Ни одна анимация не задерживает изменение DOM или состояния. Закрытие оверлея сразу снимает модальность и `inert`.
3. Единственная пауза ввода — View Transition. Его анимация длится не больше 165 мс, а вся пауза — это анимация плюс снимки и колбэк обновления, несколько кадров (§6.6.2). Запущенный переход пропускается новым. j/k не запускает переход. Одно действие пользователя даёт не больше одного перехода: открытие статьи на телефоне, «Назад» (кнопка, Escape, жест или кнопка браузера через `popstate`), открытие и закрытие оверлеев истории и глубокой ссылки (§6.6.1). Правила перехода внутри документа действуют только под `html[data-rf-vt]` и не меняют кросс-документный переход (§6.6.2).
4. После окончания или останова анимации inline-стиль цели такой же, как до неё. Обычно это значит: нет inline `opacity`, `transform`, `scale`, `translate` и нет пользовательских свойств `--scale`, `--translate*`. Исключение — inline `transform` свайпа, которым владеет `read.js`. Средство — пять правил обёртки движка (§6.1).
5. Ни одна анимация не длится дольше `--t-slow`, пружины тоже (они обрезаются на бюджете, §6.3). Частые действия укладываются в `--t-fast-max` целиком, считая пружину; нажатие — один вызов без удержания (§6.4.3).
6. Слой никогда не пишет текст и не меняет структуру в элементах, которыми владеет другой код. Временная графика (только частицы звезды) живёт только в `#rf-motion-layer`.
7. Узлы в `#rf-motion-layer` инертны, без id и без `data-*`/`hx-*`, не попадают ни в один селектор модулей и не рисуются над перекрытой звездой (§6.4.2).
8. Конечное (покоящееся) отображение каждого экрана с анимацией и без неё совпадает попиксельно.
9. Анимация вызывается только из `motion.js`, и только через публичный API anime.js. Вне его разрешены ровно четыре вещи:
   - `RFMotion.play('swipe-snap', …)` в `read.js`;
   - `RFMotion.play('flash', …)` в `feeds-settings.js`;
   - в `app.js` ровно один `RFMotion.transition(` — внутри помощника `_shellTransition(key, fn)`. Сам помощник вызывается ровно в шести местах из таблицы §6.6.1. Ключ — литерал из закрытого списка: `mobile-detail-open:on`, `mobile-detail-open:off`, `story-detail-open:on`, `story-detail-open:off`, `deeplink-detail-open:off`. Единственная другая допустимая форма — тернарное выражение ровно из двух литералов этого списка (место 3);
   - галерея `/dev/ui` (`templates/dev/ui.html`): `RFMotion.enter(` (уже есть, `:392, 417`) и `RFMotion.play(` для кнопок Replay (§6.13). Это страница разработчика, а не продукт, и её inline-скрипт уже существует. **Решение планировщика:** галерея — единственное исключение из анти-цели «inline-скрипт в шаблонах» (§2), и только для этих двух вызовов.

   Новый прямой вызов — это нарушение, его ловит проверка (§9). Модули могут отправлять доменные события (`rf:settingreverted`): это не вызов анимации.

   **По этапам.** Проверка `check-motion-calls.mjs` появляется в этапе 1 как список разрешённого **с верхними границами**: не больше одного `RFMotion.transition(` в `app.js`, и только внутри `_shellTransition`; не больше шести вызовов помощника; ключи только из списка; `play` только с указанными именами и в указанных файлах; в галерее только `enter` и `play`. В этапе 1 вызовов ещё нет, и проверка зелёная. `read.js` переходит на `play('swipe-snap')` в этапе 2, помощник и шесть мест появляются в этапе 2, `play('flash')` — в этапе 4. Ровно шесть вызовов помощника проверяет юнит-тест этапа 2 (§9, п. 12). **Решение планировщика.**
10. Офлайн: снимки не меняются без повышения версии; в этой работе снимки не меняются вовсе (§6.7); drift-тест зелёный; оболочка работает офлайн; CSP без нарушений.
11. Ни одно правило reduced motion не ставит `transition: none` на элемент, у которого Basecoat ждёт `transitionend`, в том числе через `[data-motion]` (§6.11).
12. OOB-свап и замена на месте с тем же id никогда не проигрывают появление и не двигают соседей (§6.4.1, §6.4.2).
13. Одна смена состояния или числа даёт не больше одной анимации на цель (§6.4.4, §6.4.6).

## 13. Риски

- **Внутреннее поведение anime 4.5.0.** Чистота inline-стилей опирается на фиксацию в конце, `revert()` и позднее событие `cancel` (§3), а это не документированный контракт. Смягчение: пять правил обёртки (§6.1), проба в Chrome 158, e2e «Без следов» (§9, e2e 5), который при обновлении anime скажет, если поведение сменилось.
- **FLIP на чужих раскладках** (таблицы, flex-wrap чипов): сдвиг `translate` у `<tr>` и у чипов считается по прямоугольникам, а не по структуре. Смягчение: короткая длительность, не больше 10 соседей, e2e «Без следов» на таблице источников.
- **Наблюдатель на всё `body`** при больших свапах. Смягчение: флаг свапа цели, фильтр по атрибуту и старому значению, работа в `requestAnimationFrame`.
- **Кросс-документный VT** блокирует отрисовку новой страницы до готовности перехода. Смягчение: длина ≤ 165 мс, только `no-preference`.
- **Подмена `close()` у листа** зависит от внутреннего устройства Basecoat 1.1.0. Смягчение: e2e-тест на мгновенное закрытие; при обновлении Basecoat тест скажет, если что-то сломалось.
- **Обёртка `document.startViewTransition`** опирается на то, что htmx берёт свойство в момент вызова (проверено в 2.0.4). Смягчение: юнит-тест 13 и e2e «один переход на действие» на настоящем htmx.
- **WebKit**: View Transitions внутри документа есть в Safari 18, кросс-документные — с 18.2. На старых версиях переходов просто нет.
- **`swapOverride` и порядок событий htmx.** Включение перехода опирается на публичное поле `detail.swapOverride` и на то, что `afterSwap` приходит на новые элементы `outerHTML`-OOB (§3, проверено в 2.0.4). Смягчение: юнит-тесты 5 и 11 (§9) идут на настоящем `htmx.min.js` в jsdom, как уже делают `tests/js/offline-sync.test.mjs` и `ui-sources.test.mjs`, а не на заглушке, и при обновлении htmx скажут, если поведение сменилось.
- **Отложенное обновление оболочки.** Класс полноэкранного состояния меняется примерно через кадр после действия. Смягчение: склейка по ключу, сброс на `beforeSwap` и `keydown`, перечень читателей в §6.6.1, e2e «один переход на действие».

## 14. Решения планировщика (сводка)

1. Один движок — `anime.waapi.animate` из публичного API anime; без прямого `Element.animate`; без anime — без анимации. JS-движок `anime.animate` не используется, `RFMotion.animate` и `stagger` удаляются в этапе 4 (§6.1).
2. Пять правил обёртки движка: `revert()` в `onComplete`, массивы ключевых кадров, последний кадр — покой (сначала останов своих анимаций того же элемента и свойства; `none` для `scale`/`translate`; вычисленный стиль для `opacity`, пропуск при идущем CSS-переходе `opacity`; единственное исключение — `visibility` при закрытии листа сайдбара), без `persist`, останов через нативный `cancel()` (§6.1).
3. Только родные имена свойств `opacity`/`scale`/`translate` (у листа сайдбара `transform`/`visibility`); ключи `x`/`y`/`translateX`/`scaleX` запрещены (§6.1).
4. Один файл `motion.js`, при росте — второй статический файл того же слоя (§6.1).
5. Длительности токенов не меняются; новые `--rf-stagger-step`, `--rf-stagger-max`, `--rf-ease-overshoot`; `--t-press` не вводится (§6.3).
6. Пружины `anime.spring` → `anime.waapi.convertEase`, обрезанные на бюджете с нормировкой; бюджет `pop` — `--t-med-max` (§6.3).
7. Особые эффекты привязаны к существующим хукам, а не к новым атрибутам в шаблонах снимка (§6.2, §6.7).
8. Выход строк — FLIP соседей по снимку прямоугольников у причины (синхронной — клик, клавиша, доменное событие; или серверной — `beforeSwap`/`oobBeforeSwap` запроса не от опроса); призраков нет; удалённое исчезает сразу; архив строку не убирает и FLIP не даёт (§6.4.2).
9. `#rf-motion-layer` только для частиц звезды, с проверкой перекрытия через `elementFromPoint` (§6.4.2).
10. Нативное закрытие листов в `ui/dialog.js` вместо задержки 550 мс у Basecoat (§6.4.2).
11. Меню остаются на CSS Basecoat с перенастройкой и каскадом пунктов (§6.5).
12. Смена вида в читалке — каскад, а не View Transition (§6.6).
13. Кросс-документный View Transition для экранов, в этапе 1, включая публичные страницы, приветствие и share target (§6.6, §10).
14. Полноэкранные состояния через один помощник `_shellTransition` в шести местах `app.js`, со склейкой по ключу и сбросом отложенного обновления; ресайз и глубокая ссылка при загрузке не обёрнуты; `RFMotion.play` в `read.js` и `feeds-settings.js` (§6.6.1, §6.8).
15. j/k не запускает View Transition (§6.6).
16. Первый список после загрузки читалки получает каскад (§6.9).
17. Исключение `.row-just-saved` (2 с) остаётся (§6.3).
18. Спиннеры остаются под reduced motion (§6.11).
19. Свёртка разделов и ширина сайдбара остаются на CSS (§6.5).
20. Сброс reduced motion и кросс-документный переход — в этапе 1 (§10).
21. API для тестов: `RFMotion.activeCount()`, `RFMotion.idle()` (ждёт и текущий View Transition), журнал `RFMotion.trace` под `data-rf-motion-trace` (§6.1).
22. Пределы: 10 элементов каскада, 40 прямоугольников в снимке и 10 соседей FLIP, 6 частиц и 2 вспышки, 8 попов счётчиков одновременно (§6.3, §6.10).
23. Сброс reduced motion до 0,01 мс, а не `none`, только у самих компонентов для `animation` (§6.11).
24. Вето View Transition, если прошлое открытие статьи было меньше 300 мс назад; метку времени ставит обёртка при старте перехода `detail` (§6.6.2).
25. Счётчики — `count-pop` на самом бейдже, текст сразу конечный, без цифр поверх (§6.4.6).
26. Исключение первой отрисовки для `attention` и `flash` (§6.9).
27. Проверка `scripts/check-motion-calls.mjs` в `npm run check:sources` (§9).
28. Нажатие только на элементах, которые реагируют на клик; голые `[hx-get]` и строчные ссылки исключены; один вызов на `pointerdown` (`[1, ~0,94, покой]`, пружина `press`, ≤ `--t-fast-max`), без удержания и без слушателей отпускания; невидимые остаточные переходы `scale` и `translate` приняты (§6.4.3).
29. Переход при открытии статьи включает слой через `detail.swapOverride` на `htmx:beforeSwap` (полная спецификация + `transition:true settle:0ms`, только три колонки, доверенный клик, `shouldSwap`, запрос от строки или участника истории), намерение объявлено `data-motion-transition="detail"` на `#article-detail` в `main.html`; снимок и `OFFLINE_TEMPLATE_VERSION` не меняются (§6.6.2, §6.7).
30. Событие `rf:settingreverted` из `ui/settings.js` для отката настройки (§6.4.4).
31. Контейнер с `data-motion` проигрывает пресет на каждом новом ребёнке, добавлен он htmx или JS; «стал видимым» — только по четырём точным признакам со старым значением атрибута (§6.4.1).
32. Замена с тем же id — обновление на всех путях (`oobBeforeSwap` как главный сигнал, `beforeSwap` для основного `outerHTML`, пары в наблюдателе); OOB никогда не даёт появления; `oobAfterSwap` не используется; ИИ-блок — явный пресет состояния `ai-ready` (§6.4.1, §6.4.2).
33. Правила перехода внутри документа ограничены `html[data-rf-vt]`; атрибут ставит и снимает одна обёртка `document.startViewTransition` по `finished` текущего перехода, и снятие вешается на каждый переход, который она видит; без опроса анимаций и без таймера (§6.6.2).
34. Правило `[data-motion]` под reduced motion переписано на `transition-duration: 0.01ms` с `animation: none`; `.rf-flash` остаётся с `none` (§6.11).
35. Один владелец анимации на пару «статья и состояние»: звезду, прочитано и архив ведёт только доменное событие, повторы гасит память последнего значения (§6.4.4).
36. `<details>` и вкладки Basecoat анимируются общей проводкой (`toggle`, `[role=tabpanel]`) без правки шаблонов (§6.5).
37. Появление в статье играется на `<article>`, а не на обёртке (§6.4.1).

## 15. Вопросы, которые решает только владелец

1. **Частицы у звезды.** Шесть маленьких точек цвета звезды разлетаются при постановке. По умолчанию: да. Если это слишком, остаётся только пружинный «поп», и `#rf-motion-layer` не нужен вовсе: частицы — его единственная задача.
2. **Полоса обратного отсчёта на тостах с Undo (10 с).** Это новый видимый элемент, а не анимация существующего, поэтому сейчас он не входит в работу. По умолчанию: нет, записать как продолжение.
3. **Жест «смахнуть вправо, чтобы закрыть статью» на телефоне** — новое поведение. По умолчанию: нет, продолжение.
4. **Вибрация на телефоне** при фиксации свайпа (`navigator.vibrate`, только Android). По умолчанию: нет.
